This repo is the source code for 280apps.com, a platform which allows humans to easily and securely share personal apps. This repo holds the 280 CLI, backend code, and contracts.

280apps is built agent-first, with CLI conforming to the [axi.md](https://axi.md/) format.

## Who is 280 best for:

Non technical professionals building internal tools with coding agents. Basic CRUD apps with integrations, a database, file storage, etc. Their team already lives in a workplace identity system (Microsoft, Google). They cannot and should not debug deploys, configure auth, or reason about security.

280 owns the full deploy, identity, sharing, permissions pieces. Reducing the headache of a non-technical professional who is trying to build useful software for themselves and their team

## Agent-facing docs (source of truth)

Owned by the backend (`packages/backend/src/docs.ts`), served as markdown and JSON under `/v1/docs/*` via `docsRoutes()` (one-line mount in `src/api.ts`).

- setup.md (`packages/backend/src/docs/setup.md`): the entry prompt agents fetch ("Fetch https://www.280apps.com/setup.md and push"), then run `npx -y two80@latest push` (Node 20+). Section 1 embeds the support matrix inline as two small tables (supported stacks / not supported); there is no separate platform-support doc or route anymore.
- Platform support: the structured matrix in `packages/backend/src/docs.ts` serves `/v1/docs/capabilities` for the landing page `/docs` route. The agent-facing matrix now lives inline in setup.md section 1 (the standalone `platform-support.md` doc and its `/v1/docs/platform-support.md` route were removed).
- the-280-way (`the280WayMarkdown()`): the build reference agents follow; one blessed answer per need. Next.js App Router + Tailwind/shadcn; provisioned Postgres via Drizzle + serverless driver; R2 for files; identity read from `x-280-user/roles/actions` headers (never write auth); `280.json` manifest declares features, actions, secrets, crons; the Never list (no auth libs, no native modules, no fs writes, no websockets, no long running processes); loop: build with `two80 dev`, push, fix what push says, verify URL.

Product and tech vision (direction, not shipped): any app deploys (push instructs, agent converges); auth comes built in (apps hold zero login code, 280 is the front door); sharing works like Docs (grants by email/domain/link, per feature roles, custom actions, instant apply, "view as"). Locked tech decisions: Cloudflare Workers as opinionated harness; edge front door injects signed identity headers and blocks writes for readers; rolled OIDC (Google + Microsoft); per app Postgres + R2; server side builds + boot check with errors translated into agent instructions; `two80 dev` proxy injects fake identity locally. Shipped today: push, device login, deploy to Workers.

## Shipped flow (file that owns each step)

- Agent fetches setup.md (`packages/backend/src/docs/setup.md`), then runs `npx -y two80@latest push` (Node 20+).
- CLI = `packages/cli` (npm and bin `two80`). `src/push.ts`: sync, upload blobs, poll; auto-inits and bundles (`src/bundle/`). `src/app.ts` `run(env, deps)` is pure, all side effects injected via `Deps`; `src/bin.ts` is the only composition root. Stdout is TOON, proven by golden fixtures `packages/cli/testdata/*.toon` (regenerate with `UPDATE_FIXTURES=1`). `.280/config.json` (committed) binds dir to app; `~/.280/credentials` holds the machine token. Releasing: `packages/cli/RELEASING.md` (bump `package.json`, push a `cli-v*` tag, CI publishes to npm via OIDC).
- Device login: `packages/cli/src/login.ts` never blocks; prints link + code, exits `authorization_pending`; agent relays, never opens the link. User approves in the browser (their one action); re-push redeems the token.
- Backend (control plane) = `packages/backend` (npm `@280/backend`): transport `packages/backend/src/api.ts`; behavior `src/deploysvc.ts`; Postgres store `src/store/`; blobs `src/blobstore/`; runtime seam `src/seams.ts`; live substrate `src/runtime/container/` (apps run UNCHANGED as Cloudflare Containers). The transport-agnostic Hono app runs on one host today: the Node entry `src/main.ts` (direct `pg.Pool`, `S3BlobStore` over R2's S3 API, inline `InProcessActivator`, interval sweep), the Railway deploy target (`packages/backend/Dockerfile`, env documented in `.env.example`). The dead Cloudflare Workers entrypoint (`src/worker.ts`) and its per-app `AppActivator` Durable Object shim were removed once Node went live; `src/activator.ts` now holds only the live `InProcessActivator`. The runtime hands each build context to a `ContainerBuilder` (`src/runtime/container/container.ts`), constructed in `selectRuntime` (`deps.ts`): `DepotBuilder` (`depot-builder.ts`, the sole build home — daemonless remote BuildKit, one `depot build --push` to `registry.cloudflare.com`, needs `DEPOT_TOKEN`/`CLOUDFLARE_*`) is the only build path (the retired HttpBuilder/self-hosted-Docker-host and `TWO80_BUILD_*` config were deleted). The node builder `DepotBuilder` extends `RegistryContainerBuilder` (`registry-builder.ts`), which owns the shared context materialize, teardown, exec discipline, and the roll: `wrangler deploy --containers-rollout immediate` against a generated config whose container `image` is the pre-built registry ref, so no Docker runs on the roll (the old `wrangler containers apply` never existed in wrangler 4.116 and silently no-oped — report §7). Adding a build home is a new class extending that base plus one branch in `selectRuntime`; nothing above the seam changes. Depot's per-app project + the harness worker `main` (`TWO80_WORKER_ENTRY`) are wired live in the gated Railway follow-up. `platform/appcontainer/` holds `App280Container` (locked defaults: `enableInternet=false`, `interceptHttps=true`, buildpack-injected CA entrypoint). The CLI `bundle/container.ts` buildpack turns a repo into that build context (Next.js Dockerfile generated, or a user root `Dockerfile` as the escape hatch); the WfP+OpenNext path is retired. The legacy edge dispatcher (`platform/dispatcher/`) and its `apps`/`apps-development` dispatch namespaces were deleted in the Phase 3 cutover (PR fm/280-wfp-deletion); `*.280apps.run` is now served container-only by per-app Workers fronting the identity gateway (`packages/gateway`). Last blob landing triggers activation, no separate verb: the request settles the deploy (`deploysvc` settle) through the `Activator` seam (`src/activator.ts`) — on the live Node host the inline `InProcessActivator`, which claims and runs the runtime serialized per-app by a promise chain, then the CLI polls Status to a terminal state. Edge can lag ~1 min. Store SQL is schema-qualified through one `t(name)` helper (no `search_path` dependence, for transaction-mode pooling); the idempotent DDL lives once in `src/store/migrations.ts`, applied both on boot (`open()`) and by the CI-only standalone runner `src/migrate.ts` (`pnpm --filter @280/backend migrate`). Migrations are never HTTP-reachable or run at runtime by design. The two-tier permission model (design §5.4) is the flat `grants` table behind the same `Store` seam: `app_role` (owner|admin|editor|viewer) governs the app as an object, `feature_role` is builder-defined per app (custom actions fold into it via `can()`), keyed on (app_id, principal). Phase 4 wired it end to end (see the permissions bullet below).
- Contracts seam: `packages/contracts` (`deploy`, `auth`, `version` types, zod, Port), consumed by CLI and backend. The CLI bundles it (tsup `noExternal`) so npx works. Adapter subpaths (`@280/contracts/deploy/{http,fake}`, `.../auth/http`) via `exports`. `SyncResult.missing` serializes as `null` when empty.
- Agent integrations: `packages/cli/src/setup/`. `two80 setup` JSON-merges (never overwrites) a SessionStart hook into Claude Code, Codex, OpenCode and installs the skill. `packages/cli/skill/SKILL.md` is generated from the home view: `pnpm --filter two80 skill:gen`; CI runs `two80 setup --check` to fail on drift.
- Egress data path (phase 3, the security wall) = `packages/egress` (`@280/egress`): the outbound handler that attaches vault-held credentials in-flight (secret NAME crosses the DO boundary via `setOutboundByHost` params, VALUE stays Worker-side, container never sees it), the per-request call-log, the `Vault` seam, and the footgun-safe `registerEgress`/`applyEgressPolicy`. Default-deny + the fail-closed allowlist gate (HTTP 520) are enforced by `@cloudflare/containers` itself; this package owns injection, audit, and wiring. Per-app policy is the `egress` block in `280.json` (`allow` + `credentials`), parsed by CLI `bundle/container.ts`, carried in the `Manifest` (`packages/contracts` `egressPolicySchema`, folded into `canonicalDigest` so a policy change redeploys), applied per container-instance. The CI exfiltration guard is `packages/egress/test/exfil.test.ts` (drives the real handler through a faithful ContainerProxy-precedence double). Provisioned Postgres is reached through an allowlisted HTTPS endpoint using a serverless driver, never raw `:5432` (egress can block raw TCP but cannot credential-inject it). `platform/appcontainer/src/container.js` imports this package's `registerEgress`/`applyEgressPolicy` (the inline mirror is gone); the backend `Dockerfile` vendors its built `dist` into the harness Worker's `node_modules` next to `@280/gateway`/`@280/contracts`, and `platform/appcontainer/scripts/bundle-smoke.sh` proves the vendored layout bundles. Backend `deploysvc.preflight` gates typed credentials via the contract's `validateWireEgressPolicy` (validates the NORMALIZED wire form the CLI sends, which raw `validateEgressPolicy` rejects); the same helper backs the conformance fake. The phase-2 gateway is the production consumer.
- App-management dashboard = `packages/dashboard` (Next 16 / React 19, npm not pnpm). The human-facing surface for the two-tier model: dashboard (app list + per-app preview/share/view-as), login, device `activate`, and `docs`. It is a standalone npm app with its own `package-lock.json` and is deliberately excluded from the pnpm workspace (`!packages/dashboard` in `pnpm-workspace.yaml`) so it never destabilizes the backend lockfile — build it from inside the dir (`npm ci && npm run build`), not via pnpm. All backend access goes through `lib/api.ts` `apiBase()`, which requires `TWO80_API` (no host baked in; self-hostable). Deploy wiring (Railway/console) is a separate follow-up, not yet in-repo.
- Permissions/manifest/SDK (phase 4) = the enforcement of the two-tier model end to end. The app's trust boundary is the whole `280.json` — `access` (invited|anyone-at-tenant|public; the dashboard's General-access override in `app_policies.access_override` wins durably over the manifest, and `public` serves no-session visitors with a gateway-signed anonymous identity: `anon:true`, empty email, implicit viewer, no per-visit audit, `X-Robots-Tag: noindex`), `roles` (feature-role vocab), `routes` (`{path, require:{app_role|role}}`), `secrets`, `egress` — parsed by CLI `bundle/manifest280.ts` (fail-closed on malformed) and carried in the `Manifest` (`packages/contracts/src/types.ts`, folded into `canonicalDigest`; helpers `resolveRouteGate`/`routeGateSatisfied`/`appRoleAtLeast`/`appPolicyFromManifest`). Server-side `deploysvc.preflight` re-validates. When a deploy goes live, `store.finishLive` registers the policy into the `app_policies` table and seeds the owner's grant (owner resolved via apps.user_id=user.id). The gateway (`packages/gateway/src/access.ts` `Authorizer`) enforces per request: open-access mode → route gate (`no unguarded route`: an app that declares any route gates undeclared paths to owner-only; an app that declares none stays open to grants), then mints the extended signed identity (appRole/role/caps/scope) and audits the access (`store.recordAppAccess`, navigations only). `two80 push` prints the route→gate diff (`bundle/nextroutes.ts` discovers Next routes). The signed-identity scheme is one shared module `packages/contracts/src/identity.ts` (sign+verify), consumed by the gateway (mint) and `@280/sdk` (`packages/sdk`, app-facing `identity(request) → {user, can, scope}`, verifies offline against `TWO80_IDENTITY_JWKS`). Share dialog: control-plane `/internal/apps/:app/{grants,grants/revoke,share}` (session+account-owner scoped, `src/sharepage.ts` renders the two-surface HTML) + gateway `/view-as` (owner/admin-gated preview cookie). Audit event kinds: `grant.added|grant.revoked|policy.registered|app.accessed|app.access_denied`.


## Code style

Avoid comments wherever possible; make the code self-explanatory through naming and structure instead. Prefer a clear function or variable name, a named constant, or a small restructure over a comment that explains what the code does. Add a comment (2 lines maximum) only when the code genuinely cannot be made self-explanatory: a non-obvious "why", a subtle invariant, or a workaround rationale. Never restate the code, narrate the next line, or leave section-divider banners or commented-out code. Load-bearing markers (license headers, tooling directives, `eslint-disable` pragmas, machine-read annotations) stay.

## Development environment

Dev mirrors prod on isolated infra: apps deploy container-only as per-app Workers serving at `*-development.280apps.run` (fronting the dev identity gateway at `auth-development.280apps.run`), and the CLI targets it with `TWO80_API=https://api-development.280apps.com`. See `docs/dev-environment.md` for the namespace/URL/CLI-targeting details and the Railway dev variable manifest. Every env var the backend and gateway read is documented in the committed `.env.example` (names + shapes only; secrets are placeholders).
